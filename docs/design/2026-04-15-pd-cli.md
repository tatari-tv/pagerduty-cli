# Design Document: pd - PagerDuty Incident Management CLI

**Author:** Scott Idler
**Date:** 2026-04-15
**Status:** Draft (post-spike revision)
**Review Passes Completed:** 5/5

## Summary

A Rust CLI (`pd`) that replaces the manual PagerDuty UI clickops required to set
up Tatari's Incident Management workflow system. The primary use case is
programmatic creation and management of incident types, incident workflows
(WF1-WF5), incident roles, and priority verification - the configuration surface
documented in the Managed Incident Clickops Guide.

## Problem Statement

### Background

Tatari is migrating from OpsGenie to PagerDuty for incident management. The
Managed Incident system defines a structured response process: every incident
with `Incident Type = Managed Incident` triggers a full response workflow
including a dedicated Slack channel, Jira INC ticket, bookmarks, role prompts,
and priority-based status update cadence.

Five incident workflows (WF1-WF5) implement this system:

| WF  | Name                           | Trigger              | Purpose                                    |
|-----|--------------------------------|----------------------|--------------------------------------------|
| WF1 | Managed Incident Response      | Incident triggered   | Full response: Slack, Jira, bookmarks, etc |
| WF2 | Incident Visibility            | Incident triggered   | Post non-managed incidents to #incidents   |
| WF3 | Auto-Manage P1                 | Incident triggered   | Auto-set Managed for all P1s               |
| WF4a| Auto-Manage on P1 Escalation   | Priority changes     | Auto-set Managed when escalated to P1      |
| WF4b| Priority Changed               | Priority changes     | Post cadence update on priority change     |

Today, all of this configuration is done through the PagerDuty UI following a
970-line clickops guide. This is error-prone, unrepeatable, and impossible to
version control. The `terraform-pagerduty` repo handles teams, schedules, and
escalation policies, but Terraform's PagerDuty provider does not cover incident
types, incident workflows, or incident roles.

### Problem

There is no programmatic way to configure PagerDuty's incident management
workflow layer. The configuration lives in the UI, cannot be diffed, cannot be
reviewed, cannot be rolled back, and cannot be reproduced if the account is
reset. Two existing PagerDuty CLIs (martindstone/pagerduty-cli, abandoned Oct
2024; PagerDuty/go-pagerduty CLI, version 0.0.0 sidecar to a Go library) do not
cover incident types, incident workflows, or incident roles.

### Goals

- Replace the clickops guide with repeatable CLI commands
- CRUD for incident types (Managed Incident, Business Incident)
- CRUD for incident workflows including steps
- CRUD for workflow triggers (separate API resource that binds workflows to firing conditions)
- Read/verify priority configuration (P1-P4)
- Discover available workflow actions and their input schemas
- Enable idempotent "apply" patterns: run the same commands twice, get the same state
- JSON output for scripting, human-readable output for interactive use

### Non-Goals

- Terraform provider or IaC declarative state management (this is an imperative CLI)
- Incident response operations (ack, resolve, reassign) - the MCP handles this
- Incident roles management (IC, TL, CL) - **no public REST API exists**; must be configured manually in the PD UI (see Spike Findings below)
- Team, schedule, or escalation policy management (Terraform handles these; nice-to-have later)
- Event orchestration management (separate concern from IM workflow setup)
- Service CRUD (Terraform)
- OAuth flows or Jira Cloud integration setup (requires browser-based OAuth)

## Proposed Solution

### Overview

A Rust CLI binary named `pd` that wraps the PagerDuty REST API. It authenticates
via API token (from config file or environment variable), makes HTTPS requests to
`api.pagerduty.com`, and outputs JSON or human-readable tables.

The CLI follows the two-stage Cli/Config pattern: clap derives parse the command
line, then a Config layer resolves authentication and defaults.

> **Binary name:** Cargo.toml must include a `[[bin]] name = "pd"` section.
> The package name remains `pagerduty-cli` for crate identity; the binary is `pd`.

### Architecture

```
pd <resource> <action> [flags]

Resources:
  incident-type       Manage incident types
  incident-workflow   Manage incident workflows (WF1-WF5)
  trigger             Manage workflow triggers (binds workflows to firing conditions)
  action              Discover available workflow actions and their input schemas
  priority            View and verify priority levels

Utility:
  rest                Raw REST API passthrough (pd rest GET /some/path)

Future resources (nice-to-have):
  team                Manage teams
  schedule            Manage schedules
  escalation-policy   Manage escalation policies
  service             Manage services
```

#### Component Layout

```
src/
  main.rs              # thin shell: parse args, call lib, exit codes
  lib.rs               # dispatch to resource modules
  cli.rs               # clap structs: Cli, Commands, subcommands
  config.rs            # Config: auth token resolution, output format
  client.rs            # HTTP client: reqwest, auth headers, pagination, rate limiting
  output.rs            # JSON vs table rendering, IsTerminal detection
  resources/
    mod.rs             # re-exports
    incident/
      mod.rs           # re-exports for incident-type, incident-workflow
      types.rs         # incident-type CRUD
      workflows.rs     # incident-workflow CRUD (including steps)
    trigger.rs         # workflow trigger CRUD (separate API resource)
    action.rs          # workflow action discovery (read-only)
    priority.rs        # priority list/verify
```

#### HTTP Client

A thin `PdClient` struct wrapping `reqwest::Client`:

- Base URL: `https://api.pagerduty.com`
- Auth header: `Authorization: Token token=<api-token>`
- Content-Type: `application/json`
- Pagination: offset-based (`limit`, `offset`, `more` fields)
- Rate limiting: respect 429 responses with Retry-After header
- Error responses: parse PD's structured JSON error bodies (especially 400s from action input validation and PCL syntax errors) into human-readable messages. For PCL errors, include a reference to the PCL overview doc.
- All responses wrapped in resource-keyed envelopes (e.g., `{"incident_type": {...}}`)

```rust
pub struct PdClient {
    http: reqwest::Client,
    base_url: String,
    token: String,
}
```

### Data Model

#### API Envelope Pattern

PagerDuty wraps single resources in a keyed object and lists in a keyed array
with pagination metadata:

```json
// Single resource
{"incident_type": {"id": "...", "name": "..."}}

// List response
{"incident_types": [...], "limit": 25, "offset": 0, "more": false}
```

#### Core Structs (derived from go-pagerduty + MCP models)

```rust
// Incident Types - from go-pagerduty incident_type.go
struct IncidentType {
    id: Option<String>,
    name: String,
    display_name: String,
    description: Option<String>,
    enabled: bool,
    parent: Option<ApiReference>,  // parent_type on create
}

// Incident Workflows - from MCP incident_workflows.py
struct IncidentWorkflow {
    id: Option<String>,
    name: String,
    description: Option<String>,
    is_enabled: bool,
    steps: Option<Vec<Step>>,
    team: Option<TeamReference>,
}

struct Step {
    id: Option<String>,
    name: String,
    description: Option<String>,
    action_configuration: ActionConfiguration,
}

struct ActionConfiguration {
    action_id: String,            // e.g., "pagerduty.create-slack-channel"
    description: Option<String>,
    inputs: Option<Vec<ActionInput>>,
    outputs: Option<Vec<ActionOutput>>,
}

struct ActionInput {
    name: String,
    value: String,                // Liquid templates go here
    parameter_type: Option<String>,
}

// Priorities - from go-pagerduty priorites.go
struct Priority {
    id: String,
    name: String,
    description: String,
    color: Option<String>,
    order: Option<u32>,
}

// Workflow Triggers - from PagerDuty OpenAPI spec (separate CRUD resource)
struct WorkflowTrigger {
    id: Option<String>,
    trigger_type: TriggerType,         // conditional | manual | incident_type
    condition: Option<String>,         // PCL condition string (for conditional type)
    incident_types: Option<Vec<String>>, // incident type IDs (for incident_type type)
    workflow: WorkflowReference,       // references workflow by ID
}

enum TriggerType {
    Conditional,   // fires when PCL condition matches on an incident
    Manual,        // fires only when manually invoked
    IncidentType,  // fires when incident has a matching incident type
}

// Workflow Actions - from PagerDuty OpenAPI spec (read-only discovery)
struct WorkflowAction {
    id: String,
    name: String,
    description: Option<String>,
    domain_name: String,        // e.g., "pagerduty"
    package_name: String,       // e.g., "slack"
    function_name: String,      // e.g., "create_dedicated_channel"
    // action_id = "{domain_name}.{package_name}.{function_name}"
    inputs: Vec<ActionInputSchema>,
    outputs: Vec<ActionOutputSchema>,
}
```

### API Design

#### Incident Types

```
pd incident-type list [--filter enabled|disabled|all]
pd incident-type get <id-or-name>
pd incident-type create --name <name> --display-name <display> [--description <desc>]
pd incident-type update <id-or-name> [--display-name <display>] [--description <desc>] [--enabled]
pd incident-type field list <type-id-or-name>
pd incident-type field create <type-id-or-name> --name <name> --data-type <type> --field-type <type>
```

API endpoints (from go-pagerduty):
- `GET /incidents/types`
- `POST /incidents/types`
- `GET /incidents/types/{id_or_name}`
- `PUT /incidents/types/{id_or_name}`
- `GET /incidents/types/{id_or_name}/custom_fields`
- `POST /incidents/types/{id_or_name}/custom_fields`

#### Incident Workflows

```
pd incident-workflow list [--query <filter>]
pd incident-workflow get <id> [--include steps]
pd incident-workflow create --name <name> [--description <desc>] [--from-file <yaml>]
pd incident-workflow update <id> [--name <name>] [--description <desc>]
pd incident-workflow delete <id>
pd incident-workflow enable <id>
pd incident-workflow disable <id>
pd incident-workflow export <id>               # dump to YAML for version control
pd incident-workflow import <yaml-file>        # create or update from YAML definition
```

API endpoints (from MCP server):
- `GET /incident_workflows`
- `GET /incident_workflows/{id}`
- `POST /incident_workflows`
- `PUT /incident_workflows/{id}`
- `DELETE /incident_workflows/{id}`

The `--from-file` / `export` / `import` pattern is critical: it allows workflow
definitions (including all steps, action IDs, Liquid templates, trigger
conditions) to be stored as YAML files in Git. This is the "infrastructure as
code" answer for the gap Terraform cannot fill.

Example workflow YAML (WF3 - simple, one step):

```yaml
# Workflow definition (maps to POST /incident_workflows)
workflow:
  name: Auto-Manage P1
  description: Automatically set Incident Type to Managed Incident for all P1 incidents
  is-enabled: false
  steps:
    - name: Set Incident Type
      action-id: pagerduty.incident-management.update-incident-type  # real ID from pd action list
      inputs:
        - name: incident_type
          value: Managed Incident

# Trigger definition (maps to POST /incident_workflows/triggers - separate API call)
trigger:
  trigger-type: conditional
  condition: "incident.priority matches 'P1'"  # PCL condition string
```

Example workflow YAML (WF1 excerpt - complex, 8 steps):

```yaml
workflow:
  name: Managed Incident Response
  description: >-
    Full response for all managed incidents P1-P4: Slack channel, Jira INC,
    roles, status updates, PIR
  is-enabled: false
  steps:
    - name: Create Slack Channel
      action-id: pagerduty.slack.create-dedicated-channel  # real ID from pd action list
      inputs:
        - name: channel_name
          value: "incident-{{incident.created_at | date: \"%Y%m%d-%H%M\"}}"

    - name: Set Channel Topic
      action-id: pagerduty.slack.set-channel-topic
      inputs:
        - name: topic
          value: >-
            P{{incident.priority.name}} | {{incident.title}} |
            Service: {{incident.service.name}} |
            IC: TBD | Tech Lead: TBD | Comms Lead: TBD | Status: Active

    - name: Post Status Card
      action-id: pagerduty.slack.send-message
      inputs:
        - name: channel
          value: "{{steps.create_slack_channel.channel_id}}"
        - name: message
          value: |
            :rotating_light: *Managed Incident Declared* :rotating_light:

            *Title:* {{incident.title}}
            *Severity:* P{{incident.priority.name}}
            *Service:* {{incident.service.name}}
            *PagerDuty:* {{incident.html_url}}

    - name: Create Jira Issue
      action-id: pagerduty.jira-cloud.create-issue
      inputs:
        - name: project
          value: INC
        - name: issue_type
          value: "Incident (PD)"
        - name: summary
          value: "{{incident.title}}"
    # ... (4 more steps: bookmarks, #incidents post, delay, status reminder)

trigger:
  trigger-type: incident_type
  incident-types:
    - Managed Incident   # resolved to ID at import time
```

The YAML has two top-level sections: `workflow` (maps to the workflow CRUD API)
and `trigger` (maps to the separate trigger CRUD API). The `export` command
produces this format from live PD state; the `import` command translates it back
to API payloads. Liquid template strings are passed through verbatim - the CLI
does not evaluate them.

**Three-step atomic import:** `pd incident-workflow import` executes three API operations:

1. **Workflow:** Look up by name. If exists, PUT to update. If not, POST to create.
   **Always set `is_enabled: false`** regardless of the YAML value.
   This returns the workflow ID.
2. **Trigger:** Look up existing triggers for this workflow ID. If a trigger exists,
   PUT to update. If not, POST to create, referencing the workflow ID.
3. **Enable:** If the YAML specifies `is-enabled: true` AND step 2 succeeded,
   PUT the workflow with `is_enabled: true`.

This three-step sequence ensures atomicity: a workflow is never enabled with a
stale or missing trigger. If step 2 fails, the CLI reports the error and prints
the workflow ID. The workflow exists but is disabled, so it cannot fire on
outdated trigger conditions. If step 3 fails, the workflow is correctly
configured but disabled - safe to retry.

**Idempotent:** Running the same import twice produces the same state. Name-based
lookup for workflows; workflow-ID-based lookup for triggers. If multiple
workflows share the same name, the CLI errors and requires `--id` to
disambiguate.

#### Workflow Triggers

Triggers are a **separate API resource** that bind a workflow to a firing
condition. Creating a workflow does not make it fire - a trigger must be created
and linked to it.

```
pd trigger list
pd trigger get <id>
pd trigger create --workflow-id <wf-id> --type <conditional|manual|incident_type> [--condition <pcl>] [--incident-types <id,...>]
pd trigger update <id> [--condition <pcl>] [--incident-types <id,...>]
pd trigger delete <id>
pd trigger create-for-service <trigger-id> --service-id <svc-id>
pd trigger remove-from-service <trigger-id> --service-id <svc-id>
```

API endpoints (from PagerDuty OpenAPI spec - confirmed):
- `GET /incident_workflows/triggers`
- `POST /incident_workflows/triggers`
- `GET /incident_workflows/triggers/{id}`
- `PUT /incident_workflows/triggers/{id}`
- `DELETE /incident_workflows/triggers/{id}`
- `POST /incident_workflows/triggers/{id}/services`
- `DELETE /incident_workflows/triggers/{trigger_id}/services/{service_id}`

Trigger types:
- `incident_type`: fires when incident has matching type. Used by WF1 (type = Managed Incident), WF2 (type != Managed Incident)
- `conditional`: fires when PCL condition matches. Used by WF3 (priority = P1), WF4a (priority changed to P1 AND type != Managed), WF4b (priority changed AND type = Managed)
- `manual`: fires only when manually invoked via API or UI

#### Workflow Actions (read-only discovery)

Actions are the building blocks of workflow steps. Each action has an ID, typed
inputs, and typed outputs. The CLI can list all available actions so the user
knows what `action_id` values to use in workflow YAML files.

```
pd action list [--query <filter>]
pd action get <id>
```

API endpoints (from PagerDuty OpenAPI spec - confirmed):
- `GET /incident_workflows/actions`
- `GET /incident_workflows/actions/{id}`

Action IDs follow the pattern `{domain_name}.{package_name}.{function_name}`.
The `get` command shows the full input/output schema for an action, which tells
the user what `inputs` to configure in their workflow YAML steps.

#### Priorities

```
pd priority list
pd priority verify              # check P1-P4 match Tatari's severity matrix
```

API endpoints (from go-pagerduty):
- `GET /priorities`

### Implementation Plan

#### Phase 0: API discovery spike -- COMPLETED
**Model:** opus

Findings from the PagerDuty OpenAPI spec (`~/pd/docs/developer/openapiv3.json`):

1. **Triggers are a separate CRUD resource** at `/incident_workflows/triggers`
   with their own create/read/update/delete lifecycle. A trigger references a
   workflow by ID and specifies firing conditions via `trigger_type`
   (conditional, manual, incident_type) and either a PCL `condition` string or
   an `incident_types` array. This means the `import` command is a two-step
   transaction: create workflow, then create trigger.

2. **Incident roles have NO public REST API.** Zero paths in the OpenAPI spec.
   Only `UserRole` (admin/user/observer) exists. Incident roles (IC, TL, CL)
   are UI-only. Phase 4 (incident roles) is removed from scope; roles must be
   configured manually per the clickops guide.

3. **Action IDs** follow `{domain_name}.{package_name}.{function_name}` format
   and are discoverable via `GET /incident_workflows/actions`. The exact IDs
   for Slack, Jira, and PD Incident Management actions will be resolved when
   Phase 3 runs `pd action list`.

4. **Workflow steps are part of the workflow body** - a single POST creates the
   workflow with all its steps. The trigger is the only separate call.

**Remaining unknown:** Whether PUT on a workflow replaces the steps array
entirely or merges it. Must be tested live in Phase 3.

## Alternatives Considered

### Alternative 1: Extend Terraform PagerDuty provider
- **Description:** Add incident_type, incident_workflow, incident_role resources to the official Terraform provider
- **Pros:** Declarative, state management, fits existing IaC workflow
- **Cons:** Upstream dependency (PagerDuty maintains the provider), slow PR cycle, incident workflows are complex nested objects that map poorly to HCL
- **Why not chosen:** Terraform is the right tool for stable infrastructure (teams, services, EPs); an imperative CLI is better for workflow development where you iterate rapidly and need export/import

### Alternative 2: Python CLI wrapping the MCP server
- **Description:** Build a Click-based Python CLI reusing the MCP server's client code
- **Pros:** MCP already has incident workflow models, faster to prototype
- **Cons:** Python distribution is harder (requires venv/pipx), MCP models are read-heavy (list/get) not write-heavy, doesn't match team's toolchain conventions
- **Why not chosen:** Rust aligns with existing toolchain (scaffold, cargo, otto ci, bump)

### Alternative 3: CLI-Anything harness
- **Description:** Use HKUDS/CLI-Anything framework to generate a PagerDuty harness
- **Pros:** Agent-native, community distribution via CLI-Hub
- **Cons:** Research project, Python, framework dependency, no PagerDuty harness exists
- **Why not chosen:** Overhead of framework for a focused, well-defined CLI

### Alternative 4: Use go-pagerduty CLI directly
- **Description:** Fork and extend the Go CLI in PagerDuty/go-pagerduty
- **Pros:** Already has 90+ commands, active library maintenance
- **Cons:** Missing incident types, workflows, roles (the exact things we need); Go not in team toolchain; version 0.0.0 signals "not a real product"; CLI is secondary to the library
- **Why not chosen:** Would require adding the most complex resources to someone else's library-first repo

### Performance

Not a concern. This is a configuration tool, not a data pipeline. Typical
session is 1-5 API calls. Rate limiting (900 req/min on PD REST API) will never
be hit in normal use.

### Security

- API token stored in config file (mode 0600) or environment variable
- Never log or display the token value
- All requests over HTTPS (PD rejects HTTP)
- Token has account-level or user-level scope - the CLI operates within whatever
  permissions the token grants

### Testing Strategy

- **Unit tests:** Inject fake HTTP responses, verify request shapes match PD API
  expectations. Use Go structs from go-pagerduty as the reference for field names
  and JSON keys.
- **Workflow YAML tests:** Parse each of the five Tatari workflow YAML files and
  verify they produce valid API request bodies.
- **E2E smoke:** Binary runs, prints help, parses known subcommands.
- **Manual integration:** Test against Tatari's PD account using the test service
  pattern from the clickops guide.

## Risks and Mitigations

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| PUT on workflow merges steps instead of replacing | Medium | High | Test in Phase 3 with a simple workflow. If merge, implement step-level diffing (delete orphans, update existing, add new) |
| Name-based idempotency ambiguous (duplicate names) | Low | Medium | Error on multiple matches, require `--id` flag to disambiguate. Warn on import if name already exists |
| Trigger creation fails after workflow creation | Low | Medium | Three-step import: workflow always created disabled; only enabled after trigger succeeds. Report error with workflow ID for retry. |
| PCL condition syntax wrong for WF3/WF4a/WF4b | Medium | Medium | Test with simplest PCL condition first; use `pd rest` to inspect existing triggers for syntax examples |
| PagerDuty API changes break structs | Low | Low | Serde `deny_unknown_fields` off (default); extra fields ignored gracefully |
| Liquid templates invalid but accepted by API | Medium | Medium | Document that PD validates Liquid at runtime not at POST time. Recommend testing via `pd incident-workflow import` + manual incident on test service |
